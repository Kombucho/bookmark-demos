Code search

Wick is twelve files in the browser: source, a README, a log, and two configs. One reader opens them from the top and takes each file whole. The other returns passages with a path and a line. The counters are characters and words actually pulled into the answer.

Wick is not a real project, and this page does not run XERJ. BM25 here is Okapi over these files. The vector is a hand-written lexicon of six buckets, not a model and not XERJ’s embedder. Symbol chunks come from a brace matcher standing in for tree-sitter.

    The six buckets in the toy vector

    Each word was assigned by hand. A passage’s vector is the count of those words, then cosine similarity with the query. Equal cosines break toward the passage with more of those words. Nothing was learned from data.

    Flat windows are six lines, and an identifier such as rotateSegment stays one token, so the query word “rotate” does not hit it. Symbol chunks are one function each. The name is split on camel case, and the lines of the body stay with it. Docs become sections, the log becomes lines, and a repeated warning is shown once so it cannot fill the list. The small “×” is how many copies were collapsed. Config files are one record, and their keys split the same way.

    Characters are the passage or file text. Tokens drop numbers and a short stop list. They are not tokens from a model tokenizer. The whole-file counter climbs only for files the walker has opened. The passage counter is the text of the cards on the right.

    XERJ is a local-first search engine and MCP server: one Rust binary, Apache-2.0. Its README describes xerj autoindex over a folder of code, docs, logs, PDFs, and structured files; tree-sitter indexing that keeps symbols and file:line context; BM25, vector, and hybrid retrieval; an MCP server started with xerj mcp; and an Elasticsearch-compatible API. This page is a sketch of that contrast, on a tree small enough to read. It does not speak that API, and it does not reproduce any measurement published for XERJ.
