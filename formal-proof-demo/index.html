Tests and proofs

Each function has a security property and a handful of unit tests. The tests pass. The square is every byte the function can be given. Checking it either colors the whole domain green or puts a finger on a counterexample the tests never tried.

This is a loop from 0 to 255 written in JavaScript. It stands in for a prover only because the domain is tiny. It is not Rocq, it does not look at machine code, and these three functions are not the libraries in the post. A real proof is an argument a checker accepts. Here, trying every input is the argument.

    The bounds property is index < length. The length property is: a product that fits in one byte is returned exactly, and a product that does not is refused. The copy is allowed exactly when start + count <= capacity using the real sum. A low byte left over after the sum passes 255 is not a small end. The guard subtracts only after count is known to fit, so that comparison cannot wrap.
    
    
    Fuzzing, as the post describes it, pushes a great many generated inputs through an entry point and still cannot finish: there are always more inputs. The spec they proved says a compiled fuzz entry point never crashes for any input under 64 MB, for every modeled Linux response and memory layout. The assumptions named in the post are a single-threaded static binary, a fixed memory budget, a RISC-V CPU, and Linux. Claude wrote the proofs. The Rocq kernel checked them. The trusted pieces they list are the RISC-V model, the Linux process model, the theorem statements, and Rocq itself. “Formally verified” there does not mean bug-free. A checker cannot tell you that the spec matches the machine people actually run.
    
    
    Over a few weeks they patched bugs found along the way and then proved no crash, including AddressSanitizer failures and failed assertions, for 239 entry points across 123 OSS-Fuzz libraries. The proofs are about the compiled RISC-V instructions. The post says they come to about 180 million lines of Rocq, with a typical proof around 600,000 lines, on binaries whose median length is about 18,000 instructions. This page’s 65,536 or 16,777,216 checks are not that. Enumeration only works because a byte is small and the functions are a few lines long.
