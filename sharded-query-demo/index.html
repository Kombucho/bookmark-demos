One join, four shards

Sharded query

A router pretends to be Postgres. Follow one join from the handshake to the rows coming back, then move orders onto the customer’s shard and watch the router join disappear.

The statement

Customer name, order total, and placement time for recent orders. $1 is the cutoff, 9 Sep 2026 in this walkthrough.

SELECT customers.name, orders.total, orders.created_at
FROM customers
JOIN orders ON orders.customer_id = customers.id
WHERE orders.created_at >= $1;

    Eight customers and twelve orders are drawn on the shards so the placement is visible. The sliders are the statistics a planner would use, not the toy rows. A real router hashes the shard key and picks a range. Here the toy key is id mod 4, so a row’s shard is obvious.

    The cost model is a sketch: a shard request is expensive, a row held in the router is not, until the build side is large. Nested loop from the orders side can win when only a few orders qualify, because a customer lookup hits one shard. Nested loop from the customers side almost never wins here: each probe still visits all four shards.
